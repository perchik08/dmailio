# Маркетинговые рассылки Dmailio — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. Разработка выполняется в отдельном чате; этот документ не запускает реализацию.

**Goal:** Полностью рабочие списки подписчиков, три редактора и маркетинговые рассылки с отчётами в едином Dmailio.

**Architecture:** UI Dmailio → закрытый серверный адаптер → listmonk/PostgreSQL → выделенный массовый транспорт. Существующий outreach/SQLite сохраняет собственные очереди аутрича и прогрева; контакты связываются через устойчивые ID, не автоматическую подписку.

**Tech Stack:** Node.js 24+, существующий JS UI outreach, Go/PostgreSQL listmonk, React/Waypoint email-builder; Node test runner и Playwright для браузерных сценариев.

**Spec:** [Спецификация](../specs/2026-10-08-marketing-newsletters-design.md), [эпик #7](https://github.com/perchik08/dmailio/issues/7).

## Ветки и порядок

- Общая интеграционная ветка **Unisender**, создана от master, исходный коммит **2e694f5f** (полный SHA фиксируется в задаче 01).
- Рабочие ветки задач: codex/unisender-01 … codex/unisender-17, основаны на актуальной Unisender. Каждая задача — отдельный PR в Unisender, ревью и проверки перед merge.
- Этапы выполняются **последовательно**. Следующий начинается после приёмки предыдущего, а не после написания кода.
- Финальный PR: Unisender → master, затем согласованный release. До задачи 18 production не меняется. Не создавать релизные теги для промежуточной работы.
- Не смешивать master с незавершёнными ветками #2/#6 вслепую; совместимую базу собирает задача 01.
- №7 — общий эпик; дочерние задачи №15–32 хранят рабочий прогресс. Приоритет P2.
- Документационные изменения этого плана не означают выполнение задач реализации.

## Global Constraints

**Граница текущего выпуска:** один существующий кабинет Dmailio, текущий вход и общая база контактов. Новые личные кабинеты, организации, рабочие пространства, роли и разделение баз между пользователями в №7/№15–32 не разрабатываются. Защита существующего входа и серверных ключей сохраняется.

- **Задача №9 отложена полностью.** Без внешней валидации существования email.
- Собственный почтовый хостинг №4 не требуется.
- Создание письма с нуля: конструктор блоков, HTML, Markdown.
- Строки: 1, 2, 3, 4 и 6 колонок.
- «Отправлено» — транспорт принял сообщение, не гарантия доставки.
- Отсутствующие данные не заменяются нулём; никаких фиктивных успехов и элементов без действий.
- Отписки/жалобы/hard bounce сохраняются после импорта и учитываются перед передачей письма транспорту.
- Письмо и запуск — отдельные сущности; исходник и snapshot сохраняются.
- Никакой реальной отправки клиентской базе при разработке; только явно заданные тестовые адреса.
- Все интерфейсы находятся под /api/marketing; /contacts, /runs и другие сокращения в карточках — относительные пути этого пространства.
- Конкретный транспорт выбирается на этапе 09; до него тестовый transport только для тестов. Выбор GeoIP/лицензии — этап 14; реальный timer endpoint — этап 08.
- Новые пути фиксируют границы ответственности, существующие файлы повторно используются. Изменения контракта фиксируются в плане до зависимых задач.

## Review Focus

1. Две вкладки и обрыв ответа не должны терять исходник или создавать два запуска — задачи 05/11/12.
2. Отписка между расписанием и отправкой, включая реимпорт, исключает адрес — задачи 04/10/12.
3. Timeout после принятия транспортом не разрешает слепую повторную отправку — задачи 09/12.
4. Частичные/поздние delivery/open/click события не дают ложных процентов и дублей — задачи 10/13/14.
5. HTML, изображения, экспорты и поддельные ID не обходят существующий вход и защиту серверного API — задачи 02/06/14/16.

## Общий цикл каждой задачи

1. Прочитать ТЗ, контракт и доказательства приёмки предыдущего этапа.
2. Написать тест изменяемого поведения и проверить исходный сбой; затем реализовать.
3. Прогнать тесты этапа, регрессию затронутого, сборку и ручной smoke.
4. Открыть PR в Unisender с SHA, командами, результатами, миграциями и ограничениями.
5. Ревью → исправления → повторные проверки → merge → короткий smoke интеграционной ветки.
6. Только после этого закрыть задачу и перейти к следующей. При красных тестах — исправление в текущем этапе.

Команды базы: npm ci --ignore-scripts, npm test, npm run format:check в outreach; go test ./... и make build для изменённой Go-части; yarn build для изменённого frontend/email-builder и frontend. Запускать в Linux CI/контейнере, соответствующем workflow, не объявлять отсутствие локального инструмента успешной проверкой.

На этапе 01 зарегистрировать реальные suites: npm run test:marketing:unit, npm run test:marketing:integration, npm run test:marketing:e2e. Integration использует отдельный PostgreSQL/listmonk fixture; E2E — Playwright и изолированные тестовые данные. Конкретные проверки/ассерты каждого этапа перечислены ниже и в issues. Отсутствие ещё не созданного suite — не зелёная проверка. Для документационных этапов не писать тесты, повторяющие текст.
