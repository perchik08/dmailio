# Собственная инфраструктура отправки Dmailio — техническое задание

Дата: 18.10.2026. Статус: **отложено; выполнение не начато**.

Основание: [спецификация архитектуры](2026-10-18-owned-mail-infrastructure-design.md). При расхождении приоритет имеет согласованная новая редакция спецификации; исполнитель не должен выбирать противоречивые требования самостоятельно.

Назначение: передать будущей команде проверяемые требования и порядок разработки. Приведённые имена новых модулей и методов — проектный контракт, а не существующие функции. Этот документ не является командой начать реализацию.

## 1. Обязательные решения

- Движок доставки: Postal; интерфейс и бизнес-логика: Dmailio; служебная БД Postal: MariaDB; запуски/очередь/события Dmailio: PostgreSQL.
- Первый выпуск закрыт для одного нашего домена и одной существующей команды. Отдельные кабинеты клиентов не создаются.
- Развёртывание Postal — отдельный VPS/контейнерный проект. Тест, пилот и production не разделяют ключи, базы, очереди и IP без отдельного решения.
- Транспорт `owned_postal` включается флагом, по умолчанию выключенным. `connected_smtp` продолжает работать с прежними лимитами и учётом ящиков.
- При недоступности Postal не переключать задания на Яндекс/Google и не возвращать ложный успех.
- Ни выбор Postal, ни создание схемы БД не означают готовность массовой рассылки. Пилот разрешён только после сквозной приёмки ниже.

## 2. Зависимости существующего проекта

Использовать контакты, списки, отрисовку письма и PostgreSQL из `outreach/marketing/`. Не дублировать библиотеку писем и не создавать вторую копию аудитории в интерфейсе Postal.

До запуска этого транспорта нужен работающий движок маркетинговых запусков: снимок, аудитория, отписки, расписание, очередь получателей, статусы и отчёт. На дату документа этот полный цикл ещё не реализован. Если он будет готов к возобновлению, переиспользовать его; иначе задача 4 ниже включает его реализацию. Готовность текущего аутрича не считается готовностью маркетингового движка.

Вложения и выдача файлов по отслеживаемым ссылкам — зависимости соответствующих маркетинговых задач. Пока зависимость не принята, функция должна быть явно недоступна, а API отклонять такую отправку с понятной ошибкой. Нельзя показывать рабочую кнопку без результата.

## 4. Контракты и данные

### 4.1 Транспорт

Проектный интерфейс:

```ts
type Submission = {
  key: string;           // runId + recipientId + snapshotVersion
  messageId: string;     // неизменяемый RFC Message-ID
  senderDomainId: string;
  envelopeFrom: string;  // проверенный служебный Return-Path
  recipient: string;     // ровно один адрес
  mimeObjectKey: string;
  mimeSha256: string;
};
type SubmissionResult =
  | { state: 'accepted'; providerId: string; messageId: string }
  | { state: 'rejected'; code: string; reason: string }
  | { state: 'deferred'; retryAt: string; reason: string }
  | { state: 'unknown'; attemptId: string; reason: string };

interface DeliveryTransport {
  capabilities(): object;
  submit(input: Submission): Promise<SubmissionResult>;
  lookup(providerId: string): Promise<object>;
}
```

`lookup` использует только реально поддерживаемый Postal идентификатор. Поиск по локальному `key` или произвольному Message-ID не считать доступным без проверки. Если потерян API-ответ и providerId неизвестен, использовать сопоставление событий по проверенным полям; при невозможности сверки оставить `unknown`.

API timeout после отправки тела запроса не равен отказу Postal. Автоматический повтор допустим, только когда доказано непринятие предыдущего запроса или подтверждена серверная идемпотентность конкретной версии. Одного одинакового Message-ID недостаточно для гарантии отсутствия дублей.

`capabilities` описывает фактические возможности: доставка/возвраты, жалобы, вложения, поиск/сверка и отмена уже принятого задания. Значение «не поддерживается» отображается в продукте; заглушки успеха запрещены.

### 4.2 Миграции PostgreSQL

Использовать существующие `marketing.runs`, `marketing.recipients`, `marketing.events`, расширять аддитивными миграциями. Проверить текущие ограничения и зависимые API перед изменением. Добавить необходимые сущности:

- `sender_domains`: подтверждение владения, домен, DNS-статусы, Postal server/domain reference, время проверки и разрешение администратора.
- `delivery_attempts`: уникальный ключ операции, snapshot/hash, lease/heartbeat, время попытки, результат и providerId; без API-секретов в payload.
- `provider_message_map`: ID получателя/попытки и все необходимые ID Postal; уникальность соответствия.
- `webhook_inbox`: проверенный исходный event, ключ дедупликации, состояние обработки, время и ошибка.
- `delivery_policies`: лимиты и блокировки по IP/отправителю/доменам доставки, версии настроек.
- `suppression` маркетинговой рабочей области: адрес, тип/источник запрета, время; переиспользовать уже появившуюся реализацию вместо дублирования.

Уникальность email в одном запуске обеспечить и на уровне БД после нормализации; существующего `UNIQUE(run_id, contact_id)` недостаточно для адресов из нескольких источников. Архивный снимок контакта не изменяется при последующем редактировании контакта. Обработчик перед отправкой проверяет актуальный запрет независимо от снимка.

### 4.3 Статусы

| Получатель | Значение | Кто владеет следующим действием |
|---|---|---|
| `queued` | Ожидает передачи | Dmailio |
| `submitting` | Передача адаптеру с действующим lease | Dmailio; второй обработчик не отправляет |
| `deferred` с `source=dmailio` | Отложено до разрешённой попытки, Postal ещё не принял | Dmailio |
| `accepted` | Postal принял сообщение | Postal |
| `delayed` с `source=postal` | Postal ждёт повторной доставки до MX | Postal; Dmailio не повторяет submit |
| `delivered` | MX получателя подтвердил приём | Приём поздних событий продолжается |
| `bounced` / `failed` | Возврат после приёма / окончательный отказ | Событие и причина сохранены; политика исключения проверена |
| `held` | Удержано оператором/движком | Требуется разбор; не перезапускать автоматически |
| `unknown` | Нельзя достоверно установить факт принятия | Сверка или явное решение оператора |
| `cancelled` / `suppressed` | Не передано из-за отмены / запрета адреса | Не отправлять |

Открытия и клики — отдельные события, не замена статуса доставки. Для запуска: `draft`, `scheduled`, `sending`, `paused`, `completed`, `cancelled`, `needs_attention`. `completed` — все получатели имеют определённое окончательное состояние доставки либо исключены/отменены; это не означает 100% успешной доставки. Пока есть accepted/delayed, показывать ожидание результата; если остались только неопределённые/held, запуск требует внимания. Поздний возврат сохраняется и корректирует отчёт даже после завершения.

## 5. Этапы разработки и проверки после каждого этапа

Работа начинается только после отдельного согласования. Номера ниже локальные, не номера существующих GitHub issues. Каждый этап: тест ожидаемого поведения → минимальная реализация → тесты и ревью → отдельный PR в будущую ветку этого проекта. Не смешивать с текущим production-релизом.

| Этап | Результат | Проверка и условие завершения |
|---|---|---|
| 1. Проверка пригодности | Выбранная версия/digest Postal; подтверждённые условия VPS/IP/25/PTR; матрица API и лицензии | На изолированном стенде проверить submit, ответы с error внутри JSON, IDs, webhooks, timeout после принятия, TLS и управление доменами. | 3. Домены и отправители | Экран статусов владения, DNS и административной подготовки | Тесты неверного TXT/DKIM, просроченной проверки, DNS timeout/NXDOMAIN, DMARC alignment и адреса чужого домена. Основной MX не меняется; две SPF-записи не принимаются как корректные |

## 6. Измеримые условия приёмки

Это проектные цели, подлежащие проверке на согласованной конфигурации; они не обещают скорость приёма внешних MX.

1. Список из 10 000 адресов ставится в очередь пакетами; API не держит запрос на время SMTP-доставки и возвращает ID запуска не дольше 5 секунд. Подготовка аудитории асинхронна, виден её прогресс.
2. В синтетическом тесте с MX, принимающим каждое письмо не дольше 100 мс, после подготовки аудитории очередь поддерживает 5 писем/сек. не меньше 30 минут в пределах настроенных ресурсов. Это цель пропускной способности нашего контура, не гарантированная внешняя скорость.
3. CPU/RAM, длительность SQL и возраст очереди зафиксированы. Весь список/MIME не загружается единовременно в память worker; лимиты ресурсов воспроизводимы. Уточнить числовой предел памяти по результатам стенда до пилота.
4. Соблюдаются одновременно глобальный, IP, доменный и пользовательский лимиты. Снижение лимита действует на новые передачи, не сбрасывает использованный бюджет; уже принятые Postal сообщения описаны отдельно.
5. Перезапуск worker, повторный HTTP-запрос запуска и повторный webhook не создают дублей в доказуемых случаях. При неоднозначной сетевой ошибке получатель становится unknown, а не отправляется повторно автоматически.
6. У каждого accepted есть попытка, ID Postal и MIME/hash; у неизвестного результата — причина и журнал сверки. Архив не выдается за доказательство доставки.
7. Отписка до передачи блокирует письмо; постоянный bounce исключает адрес из дальнейших маркетинговых запусков рабочей области. Уже принятые Postal сообщения могут быть неотменяемы — ограничение явно видно.
8. Пользователь видит количество ожидающих, принятых Postal, доставленных до MX, ошибок, возвратов, неизвестных и исключённых. Итоговые числа сверяются с уникальными получателями, событиями и исходными ответами; delivered не равно Inbox.
9. Отсутствуют заглушки действий: каждое действие даёт подтверждённый результат либо явную ошибку с возможностью повторить безопасную операцию.
10. Проверено восстановление отдельной БД Postal, PostgreSQL и архива: RPO ≤24 ч / RTO ≤4 ч для пилота. После восстановления неопределённые передачи не отправляются автоматически.

## 7. Хранение и ограничения содержимого

До пилота согласовать и зафиксировать retention для MIME, файлов, событий, данных IP/User-Agent и технических логов. Предлагаемый старт: MIME и подробные события 30 дней, обезличенные агрегаты 180 дней; это проектная настройка, не юридическое заключение и не уже действующая политика Dmailio. Не применять её к существующим данным задним числом.

Лимит готового MIME установить после проверки ограничений Postal/MariaDB и существующего редактора; в пилоте исходное предложение — 10 МБ на сообщение с явной ошибкой до постановки в отправку. Проверять фактический размер MIME, а не только сумму исходных файлов. Если разрешены вложения, нужна принятая проверка типа/размера и вредоносного содержимого; до готовности запрещать их API.

Публичные картинки и страницы отписки доступны без входа по непрогнозируемым адресам; приватные вложения не публиковать открытым bucket. Токен ссылки нельзя использовать как разрешение читать чужие файлы или менять чужой запуск. Ссылки скачивания и аналитики не должны раскрывать email в URL.

## 8. Управление эксплуатацией

- До реального пилота назначить оператора, канал алертов, порядок остановки домена/IP и время реакции.
- Подготовить инструкции: выдача/отзыв ключей, проверка DNS, остановка новых передач, поиск потерянного события, разбор unknown, возврат/жалоба, заполнение диска, смена IP и восстановление резервной копии.
- Административная остановка не удаляет очередь или историю. Автопауза по аномалиям должна показывать измеренную причину и время, не скрывать её общей надписью «Недоступно».
- Пороговые значения bounce/complaint и график прогрева определить на этапе 1 вместе с источниками сигналов; отсутствие такой политики блокирует этап 9. Не выводить универсальные безопасные проценты из предположений.
- Поддержать отдельное выключение `owned_postal`; оно не мешает входу, контактам, редакторам, аутричу и подключённому SMTP. Уже принятые Postal задания при этом не считаются отменёнными.
- Откат — на предыдущий совместимый образ без уничтожения баз/очередей. Риск повторной доставки после возврата старой БД отдельно разобрать до пилота. Секреты и базы не выводить в логи и PR.

## 9. Смета до начала реализации

Заполнить расчёт по количеству отправок в месяц, размеру MIME, пиковым запускам, сроку хранения и требованиям к восстановлению. Включить VPS, статические IP, MariaDB/диски, S3, запросы, трафик, бэкапы, мониторинг, работу разработчика и оператора. Диапазоны 2–5 / 5–15 / 15–50 тыс. ₽ из спецификации — только инфраструктурные ориентиры.

Обязательные результаты оценки: стоимость пилота в месяц, стоимость одной тысячи писем при выбранном объёме, разовые трудозатраты, ежемесячное сопровождение, сценарий роста в 10 раз и сравнение с готовым массовым транспортом. До подтверждения бюджета ничего не заказывать.

Поставщик сервера, реальные домены/IP, версия Postal, административное provisioning, график прогрева, retention и бюджет намеренно оставлены решениями этапа 1. Это явные условия начала пилота, а не скрытые обещания реализованной функции.

Следующий шаг сейчас: сохранить документы в бэклоге со статусом «Отложено». Возвращаться к реализации только по отдельному запросу пользователя.
